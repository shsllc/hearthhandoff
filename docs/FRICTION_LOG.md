# Friction log

Format per the hackathon's optional friction-log bonus: task, what we expected, what actually happened, impact, and workaround. Newest entries at the bottom.

| # | Date | Task | Expected | Actual | Impact | Workaround |
|---|---|---|---|---|---|---|
| 1 | 2026-10-05 | Verify webhook signatures using the official sample | The sample's webhook route uses the documented HMAC `X-Signature` | The sample checks `Authorization: Bearer ${RING_WEBHOOK_SECRET}`. The API reference specifies `X-Signature: sha256=<hex HMAC-SHA256 of raw body>` | A developer copying the canonical starter would accept unsigned or spoofed webhooks, or reject real ones | Implemented the API-reference algorithm. Verified against Ring's own Python snippet (`test/ring.test.ts`) |
| 2 | 2026-10-05 | Model webhook event types from the sample | The sample schema matches documented event types | The sample's Zod enum is `motion_detected, device_added, device_removed, person_detected`. It has no `button_press` (documented) and includes `person_detected` (not documented). A real doorbell press fails validation and falls into "generic" normalization | Doorbell presses, the most useful caretaking signal, are mis-parsed by the starter | Wrote our own parser from the API reference |
| 3 | 2026-10-05 | Follow doc links from the sample README | Links resolve | `docs/ring/notifications.html` and `docs/ring/authentication.html` return 404. The content now lives as anchors inside the single `api-documentation.html` (about 1 MB) | Slowed discovery. The WebFetch-style tools we used summarized the giant page lossily and missed the payload examples | Downloaded the page and read the sections directly |
| 4 | 2026-10-05 | Determine the no-device testing path | One documented simulator that produces door events reaching our code | "Get started" lists "at least one Ring device" as a requirement. The glossary mentions a "sandbox with synthetic devices and events" without saying how to access it. The Playground (release notes only) simulates Package/Vehicle/Motion, but three independent hackathon repos report that its events don't appear in Event History or reach webhooks | Can't plan a doorbell-event demo without hardware from the docs alone | Two-tier plan. Pending our own Playground verification (entry to follow) |
| 5 | 2026-10-05 | Understand motion `sub_type` values | Stable documented vocabulary | Values depend on whether Smart Alerts is on (`motion` vs `human`/`vehicle`/`package_delivery`/`other_motion`). No API exposes that setting. Clarified in a release note dated today | Can't tell "no person detected" from "classification off" | Treat sub-type as open vocabulary. Exclude only `vehicle`. Pass unknown values through |
| 6 | 2026-10-05 | Implement the Token Exchange URL (one-way linking) | The docs show the request Ring sends to the partner endpoint (content type, field names, any signature) | The docs say only that Ring "POSTs the authorization code." No example request body, no content type, no field name, and nothing on whether the call is signed or what response Ring expects | We can't be sure our endpoint parses Ring's request until a real linking attempt | The handler accepts JSON or form bodies, looks for `code`/`authorization_code`/`auth_code`, and logs field *names* (never values) to the audit log, so the first real attempt shows the true shape |
| 7 | 2026-10-05 | Meet the 5 s webhook deadline on Lambda | n/a (AWS) | Measured on the first deploy: about 0.41 s cold-start init (including the Secrets Manager read), with 70–150 ms handler time. Well inside the limit | None so far | Dedupe makes any retries harmless. Re-measure once Ring webhooks are live |
| 8 | 2026-10-06 | Deploy a second copy of the stack (rename) | Two stacks from one SAM template coexist | SAM's `ScheduleV2` event defaults the schedule name to its logical ID (`AppFunctionTick`). Schedule names are unique per account and region, so CloudFormation early validation rejected the second stack | About 10 min lost (AWS, not Ring) | Set `Name: !Sub ${AWS::StackName}-tick` |
| 9 | 2026-10-06 | Link a real Ring account to the private app | Developer FAQ Q16: the portal's *Connect → Log in with Ring* "uses the same OAuth account linking flow as public apps — Ring sends an authorization code to your Token Exchange URL" | After *Log in with Ring* succeeded in the portal, our Token Exchange, Account Link and Webhook URLs received **no requests** (verified in Lambda logs and the DynamoDB audit trail). Ring staff in the [forum](https://community.amazondeveloper.com/t/account-linking-test-flow-never-reaches-configured-urls/28516) (2026-06-08) say the portal button only adds a staging user; the real flow must be started from the Ring **mobile app's** App Store, which also requires a US-located device | Looked like a backend bug and cost debugging time. The official FAQ contradicts staff guidance | Add the staging user in the portal, then connect from the Ring mobile app |
| 10 | 2026-10-06 | Configure account linking for a private app | The Configure docs describe *Staging settings* and *Production settings* tabs (with "Copy from staging settings") and a Default Redirect URL field | The private app's Account linking page has a single form with four fields (Account Link, App Homepage, Token Exchange, Webhook): no tabs and no Default Redirect URL | Unclear which environment a private app uses; instructions written from the docs sent us looking for a tab that doesn't exist | Treat the single form as the only configuration for private apps |
